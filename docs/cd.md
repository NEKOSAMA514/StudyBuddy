# 手动构建与 Release 草稿

CD 为 Windows x64 CPU 便携预览版准备未公开的 Release 草稿。正常推送和合并仍按 [CI 工作流](../.github/workflows/ci.yml)检查；[CD 工作流](../.github/workflows/cd.yml)只由手动运行启动，不自动公开版本。

## 首次启用

先通过 PR 把工作流及脚本合入 `main`。[GitHub 的手动运行入口](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)要求工作流已经存在于默认分支。认证使用仓库自带的 `GITHUB_TOKEN`，无需配置个人令牌；仅创建草稿的任务申请 `contents: write`。

## 创建草稿

1. 在仓库打开 **Actions → CD / Windows portable draft → Run workflow**。
2. 分支选择 `main`，填写版本号，例如 `1.0.1-beta.1`，不加 `v`。流程会使用标签 `v1.0.1-beta.1`。
3. 点击 **Run workflow**。在运行详情查看检查、构建、启动验收和草稿创建进度。
4. 成功后，在运行摘要点击草稿链接，或到仓库 **Releases** 中打开草稿。

测试、打包和草稿均固定到启动时的提交 SHA。即使运行期间 `main` 有新提交，本次产物也不会切换源码。来自其他分支的运行会失败。

流程先复用 CI 的文档检查、后端测试、便携工具测试和前端构建，再调用现有 FFmpeg 与便携包构建脚本。FFmpeg 的四份构建输入按配方和工具链版本缓存，缓存未命中时从固定源码构建；缓存命中时仍由打包脚本校验。它们用于构建，不作为 Release 附件上传。

## 附件与人工试用

默认附件只有三份：

- `StudyBuddy-v<版本>-windows-x64-preview.zip`：完整便携包。
- 同名 `.zip.sha256`：ZIP 的 SHA-256 校验值。
- `acceptance.json`：自动启动验收报告，记录版本、源码 SHA、检查结果及未执行项目。

发布前可以在草稿页面编辑标题和说明、删除或补充附件。[草稿仍可编辑，只有手动发布后才公开](https://cli.github.com/manual/gh_release_create)。流程将草稿标记为预发布版本，不设置为 Latest。

下载后先校验 SHA-256，完整解压到固定、可写目录，双击 `启动.cmd`。试用视频与文档笔记、思维导图、语音、OCR 和真实 API，再决定是否点击 **Publish release**。包内已有的待验收说明继续保留。

自动验收使用原始 ZIP 的独立副本，路径包含中文和空格；检查文件清单、首次初始化失败与重试、重复启动、端口回退、设置保存与恢复及 Ctrl+C 正常退出。上传的 ZIP 不经过初始化或修改。

该流程运行的是 `--smoke-only`，不验证实际语音、OCR、文档处理或云端 API，也不代表完成 Windows 10/11 干净系统测试。完整本机验收仍按 [便携包说明](portable.md#验证与记录)执行。

## 失败、日志与重跑

- 在 Actions 运行详情打开失败步骤，查看直接错误。构建任务上限为 120 分钟。
- 运行详情的 **Artifacts** 中保留 `portable-logs-<运行ID>-<尝试号>`，包含已有的构建日志及验收报告，保留 30 天；打包前就失败的运行可能没有这些文件。
- 所有检查通过才把三份附件传给创建草稿的任务。校验值不符、验收失败、文件达到 2 GiB 或 GitHub API 错误都会停止流程。
- 可以重跑整个流程；若只在草稿创建或上传阶段失败，可选择 **Re-run failed jobs**，复用该次已验证的附件。下载步骤按原构建任务的产物 ID 取附件。
- 已有同版本、同提交草稿时，会补齐或替换这三份默认附件，保留已编辑的说明及其他附件；手动删除的默认附件会重新上传。
- 版本已公开，或同名标签、草稿指向其他提交时，流程拒绝覆盖。新提交应使用新版本号；仅重试同一条提交可沿用版本号。
- 缓存损坏会被完整性校验拒绝。可在 Actions 的缓存列表删除对应 `ffmpeg-windows-x64-…` 缓存后重跑，重新编译。

同版本运行串行处理，不取消已经运行的构建。创建草稿和上传附件是独立请求；上传中断时可能留下附件不全的未公开草稿，修复后重跑即可，不会自动发布。
